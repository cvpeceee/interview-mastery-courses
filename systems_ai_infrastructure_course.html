2. Networking & High-Performance Interconnects

Time: 14–18 hours

Core concepts

  • Network fundamentals: latency, bandwidth, congestion, flow control
  • RDMA, InfiniBand, and GPUDirect-style interconnects
  • Collective communication (all-reduce, all-gather) and how they map to network topology
  • Topology awareness (fat-tree, dragonfly, etc.) and its impact on training jobs
  • Network observability, telemetry, and debugging
  • Multi-tenant networking and isolation

Staff-level depth

  • How collective algorithms (ring, tree, hierarchical) perform under different topologies and failure conditions
  • Congestion control mechanisms and their interaction with AI traffic patterns
  • In-network computing and where it helps or hurts
  • Diagnosing and mitigating stragglers caused by network imbalance
  • Capacity planning: oversubscription ratios, bisection bandwidth, and cost trade-offs
  • Security and isolation implications of high-performance fabrics

Strong candidates can reason about what breaks at scale, quantify trade-offs, and propose measurement-driven improvements rather than generic designs.

Interview Practice — Networking

Question 1: How would you design a network for a large GPU cluster to minimize all-reduce time?
Approach: Clarify scale and topology constraints. Discuss fat-tree or dragonfly. Explain how collective algorithms (ring, tree, recursive doubling) interact with topology. Mention RDMA and congestion control.
Follow-ups: What happens if one link fails? How do you handle multi-tenant interference?

Question 2: Explain the difference between TCP and RDMA for AI workloads.
Approach: TCP has higher latency and CPU overhead. RDMA enables kernel bypass and low latency. Discuss when each is appropriate and GPUDirect-style paths.
Follow-up: How would you debug a training job that is network-bound?

3. Inference Serving Systems

Time: 14–18 hours

Key topics

  • Batching strategies: static, dynamic, continuous batching
  • KV-cache management and memory pressure
  • Request routing, load balancing, and model parallelism for serving
  • Latency vs throughput trade-offs
  • Multi-model and multi-tenant serving
  • Systems like Triton, Dynamo, and custom serving stacks
  • Failure handling, autoscaling, and SLO management

Staff-level depth

  • How continuous batching interacts with prefill vs decode phases and memory fragmentation
  • Speculative decoding, prefix caching, and other advanced serving optimizations
  • Multi-node inference and tensor/pipeline parallelism for serving
  • Admission control, priority, and fairness under overload
  • Observability: tracing request latency breakdowns and GPU utilization metrics
  • Cost-aware serving: when to scale vs optimize, and failure domains

Strong answers include concrete failure modes (OOM, hot keys, version skew), measurement strategy, and how you would iterate on the system in production.

Interview Practice — Inference Serving

Question: Design an inference serving system that keeps p99 latency low while maximizing GPU utilization across variable request sizes and multiple model versions.
Approach: Clarify latency SLOs and traffic patterns. Discuss continuous batching, KV-cache management, request routing, and model loading. Address memory pressure and failure isolation.
Follow-ups: How do you handle a sudden traffic spike? What happens if a model version has a memory leak? How do you measure and improve utilization?

4. Embedded Systems, Firmware & Drivers

Time: 15–20 hours

Core areas

  • Real-time constraints and deterministic behavior
  • Device drivers: interrupt handling, DMA, memory-mapped I/O
  • Firmware architecture and update mechanisms (OTA safety)
  • Power, thermal, and resource constraints
  • Linux kernel concepts relevant to drivers and platforms
  • Debugging on embedded targets

Staff-level depth

  • Locking, RCU, and concurrency models in drivers
  • Power management and runtime PM interactions with latency
  • Safe OTA design including validation, atomicity, and fleet rollout strategy
  • Debugging intermittent failures on resource-constrained devices
  • Co-design with hardware teams on interrupt and DMA requirements
Interview Practice — Embedded / Drivers

Question 1: Explain how a device driver handles interrupts and DMA.
Approach: Describe top-half / bottom-half, interrupt context constraints, DMA mapping, and completion handling. Mention error paths and power management.
Follow-up: How would you debug a driver that occasionally drops data under load?

Question 2: Design a firmware update mechanism that is safe under power loss.
Approach: Dual-bank or A/B updates, atomic commit, validation, and rollback. Discuss what happens if power is lost mid-write.

5. Robotics Platforms & Real-Time Systems

Time: 12–16 hours

Key concepts

  • Perception → planning → control pipelines
  • Sensor fusion and timing
  • Real-time scheduling and latency budgets
  • Safety, redundancy, and fail-operational design
  • Robot-as-a-Service platform considerations (fleet management, OTA, monitoring)
  • Simulation and hardware-in-the-loop testing

Staff-level depth

  • End-to-end latency budgeting and worst-case execution time analysis
  • Failure mode and effects analysis for safety-critical paths
  • Fleet-scale data collection, simulation fidelity, and validation strategy
  • Trade-offs between on-robot compute and cloud offload
Interview Practice — Robotics

Question: Design the software architecture for a robot platform that must meet strict control-loop latency while supporting fleet updates and remote monitoring.
Approach: Separate real-time control path from non-real-time services. Discuss sensor fusion timing, safety monitors, OTA strategy, and telemetry. Address failure isolation.
Follow-ups: What happens if a sensor fails? How do you validate a software update on a fleet?

6. Hardware/Software Co-design & Accelerators

Time: 12–16 hours

Topics

  • How software decisions affect hardware utilization and vice versa
  • Accelerator programming models and performance models
  • Memory hierarchy awareness (on-chip vs off-chip)
  • Compiler and runtime co-design
  • Profiling and optimization loops between hardware and software teams
Interview Practice — HW/SW Co-design

Question: How would you improve the performance of a workload that is currently memory-bound on an accelerator?
Approach: Profile first. Discuss data layout, tiling, memory hierarchy usage, and whether the bottleneck is hardware or software. Propose experiments and trade-offs.
Follow-up: How would you work with the hardware team if a change is needed?

7. Performance Engineering & Kernel

Time: 12–16 hours

Focus areas

  • Profiling methodology (measure first)
  • CPU and GPU performance counters
  • Cache behavior, memory bandwidth, and instruction-level optimization
  • Kernel-level performance issues (scheduling, interrupts, locking)
  • Math libraries and low-level optimization
  • Systematic approach to performance regressions
Interview Practice — Performance

Question: A system is slower than expected. Walk through how you would diagnose whether the bottleneck is compute, memory, network, or software overhead.
Approach: Establish baseline. Use profilers and counters. Isolate layers with experiments. Measure before and after changes. Discuss common pitfalls.
Follow-up: How do you prevent the same regression in the future?
